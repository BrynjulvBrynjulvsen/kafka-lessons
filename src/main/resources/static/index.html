FAILURE / AN APPLICATION RESPONSIBILITY

What if the same event returns?

Confirmation sentThe business action succeeds.
→
Crash before commitThe group's saved bookmark has not advanced.
→
Event read againShould the customer receive another confirmation?

Idempotency: repeating an event must not repeat an unwanted business effect.

Explained failure scenario, not a crash demo. Uncommitted work may be read again after restart. Stable event IDs and durable duplicate-prevention state can help, but the check and effect must be coordinated: a separate seen flag leaves another crash window. An external provider may support an idempotency key. Ask how serious a repeated payment would be. Committing before the action risks missing the action after a crash. The current in-memory notification demo does not implement durable duplicate prevention; the live capability remains backlog item 8.
